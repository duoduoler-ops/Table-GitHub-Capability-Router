# Migrate from v0.3.0 to v0.4.0

v0.4.0 introduces schema v3. It separates project grade from real deployment scope and adds the B-grade task-increment plus project-level first-real-use settlement.

## Why migration needs human input

Schema v2 records whether a capability is active, cold, disabled, reference, or quarantined, but it does not record where the real capability is installed. Schema v3 adds:

```text
deployment_scope: not-installed / project / user / global / external-service
```

The CLI never infers this value from `active`, a filesystem path, or a project grade. Grade A is evidence, not global installation.

## Safe migration from schema v2

1. Keep a recoverable copy or Git commit of the workflow root.
2. Inspect every capability record and determine its real deployment scope.
3. Run one transactional command, repeating `--deployment-scope` once per capability:

```powershell
python scripts/workflow.py migrate-v3 --root <OUTPUT_DIR> `
  --deployment-scope "public-doc-checker=project" `
  --deployment-scope "reference-patterns=not-installed"
```

4. Validate the migrated root:

```powershell
python scripts/workflow.py validate --root <OUTPUT_DIR>
```

Missing mappings, unknown capability IDs, invalid scopes, mixed record versions, or failed validation stop the operation before canonical records are replaced. Re-running the command against a valid schema v3 root returns `already_migrated`.

## Direct migration from schema v1

`migrate-v3` can also migrate schema v1 directly. In addition to one deployment-scope mapping per capability, repeat `--capability-summary PROJECT_ID=SUMMARY` for every retained/reference project. The command adds both schema v2 capability summaries and schema v3 deployment scope in one transaction.

## What changes

- `workflow.json`, project records, capability records, and distillation templates move to schema version 3.
- Every capability gains the required `deployment_scope` field.
- New capabilities start as `candidate / unverified / not-installed / explicit-only`.
- `active` requires a deployed scope; `reference` requires `not-installed`.
- The generated capability router displays deployment scope separately from management and health.
- `capability-deployment` records an approved deployment fact and evidence; it never installs or removes files.
- All derived views are rebuilt, revisions increment, and one maintenance event is appended transactionally.

## B-grade behavior after migration

- Method-only value remains B/reference and is not installed.
- A low-risk executable increment gets T0 and explicit approval for `project`-scope installation.
- The current project's first real task is T1; no separate demo or durable `project-trial` state is required by default.
- T1 pass settles to A/retained plus active/project.
- T1 failure or an inconclusive result remains B/reference and recommends uninstall; deletion still requires explicit confirmation.

v0.4.0 升级到 schema v3，把“项目等级”和“真实安装范围”拆开。迁移时必须为每条能力明确填写 `not-installed / project / user / global / external-service`，脚本不会根据 active、路径或 A 级自动猜测。

B 级只有方法价值时继续作为 reference；低风险可执行候选经过 T0 和项目级安装批准后，当前项目第一次真实任务就是 T1。通过后结算为 A/retained + active/project；失败或结论不清则保持 B/reference 并建议卸载。没有 `project-trial` 管理状态，真正删除仍需再次确认。
