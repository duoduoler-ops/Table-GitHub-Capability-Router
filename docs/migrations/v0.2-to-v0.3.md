# Migrate from v0.2.0 to v0.3.0

v0.3.0 introduces schema v2 and changes project-reference routing from one full semantic table into a mandatory thin discovery table followed by full semantic details.

## Why migration needs human input

Every approved S/A/B `retained` or `reference` project now requires one distinct `capability_summary`: a short verb + object + output sentence that tells an Agent what the saved project can add. The CLI does not guess this sentence from repository marketing or semantic examples.

Candidate, evaluated, rejected, and archived projects receive `capability_summary: none` automatically.

## Safe migration

1. Keep a recoverable copy or Git commit of the v0.2 workflow root.
2. List every project whose status is `retained` or `reference`.
3. Write one distinct capability summary for each eligible project.
4. Run one transactional migration command, repeating `--capability-summary` once per eligible project:

```powershell
python scripts/workflow.py migrate-v2 --root <OUTPUT_DIR> `
  --capability-summary "gh-owner-first=Compare repository patterns and produce a reusable decision" `
  --capability-summary "gh-owner-second=Extract a bounded workflow and produce an implementation checklist"
```

5. Validate the migrated root:

```powershell
python scripts/workflow.py validate --root <OUTPUT_DIR>
```

The migration is atomic. Missing summaries, unknown project IDs, duplicate summaries, invalid v1 records, or failed validation stop the operation before canonical records are replaced. Re-running the command against a valid schema v2 root returns `already_migrated`.

## What changes

- `workflow.json`, project records, and capability records move from schema version 1 to 2.
- Transaction manifests keep their independent schema version 1 because their file format did not change.
- Eligible project cards gain a non-empty `capability_summary`; ineligible cards use `none`.
- Record revisions increment and share one migration timestamp.
- `AGENT-ROUTER.md`, project indexes, candidate/rejection views, the project-reference routing file, and the capability router are rebuilt.
- `indexes/project-semantic-routing.md` now contains:
  - `Level 0: Thin Discovery` for cheap Top-1 discovery;
  - `Level 1: Full Semantic Routing` for examples, trigger level, and negative routing.
- A maintenance event and transaction backup are written under the workflow root.

## Routing behavior after migration

- For every substantive task with a clear object, action, or deliverable, the Agent reads the thin table once per deliverable type before concluding that no saved project is relevant.
- `high_confidence` and `gated` both allow a reminder. `gated` controls later reading or execution, not whether the project may be mentioned.
- `explicit_only` still requires the user to name or clearly request the project.
- A reminder keeps `no-extra-project`; repository reading starts only after the user chooses it, and installation or enablement still requires approval.

## 中文说明

v0.3.0 升级到 Schema v2，把原来的一张完整语义表改成“薄发现表 + 完整语义表”。迁移时必须为每个 S/A/B `retained/reference` 项目提供一条可区分的能力摘要，格式建议为“动词 + 对象 + 产物”。脚本不会根据 README 或宣传语自动猜测。

候选、已评估、否决和归档项目会自动写入 `capability_summary: none`。迁移采用事务写入：缺少摘要、项目 ID 写错、摘要重复或校验失败时，不会半迁移。完成后运行 `validate`，并检查薄发现表中每个正式项目是否只出现一行。
